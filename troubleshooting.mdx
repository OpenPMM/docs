When integrating with the Open PMM API, you may encounter a handful of recurring issues ranging from authentication failures and rate limiting to webhook delivery problems and pagination quirks. This page walks you through the most common error scenarios, explains why they happen, and gives you clear steps to resolve them quickly.

<Accordion title="401 Unauthorized">
  A `401 Unauthorized` response means the API could not verify your identity. The most common causes are:

  - The `Authorization` header is missing from the request entirely.
  - The API key is invalid, has been deleted, or was copied incorrectly.
  - The API key has expired or been rotated.

  **How to fix it**

  Confirm that every request includes a properly formatted `Authorization` header:

  ```http
  Authorization: Bearer <your-api-key>
  ```

  Check that there are no extra spaces, line breaks, or quotation marks around the key. If the key looks correct but requests still fail, navigate to your API Keys settings page and regenerate a new key, then update all clients and environment variables that reference the old one.
</Accordion>

<Accordion title="403 Forbidden">
  A `403 Forbidden` response means your API key was recognized but does not have permission to perform the requested action. This typically happens when a key was created with a limited scope that excludes the endpoint or operation you are attempting.

  **How to fix it**

  Review the scopes assigned to your current key. If the required scope is missing, create a new API key and select all the scopes your integration needs. Avoid broadening the permissions of existing production keys — instead, issue purpose-specific keys with the minimum required access.
</Accordion>

<Accordion title="404 Not Found">
  A `404 Not Found` response means the server cannot locate the resource you requested. This usually happens for one of two reasons:

  - The resource ID in your request path does not exist or has been deleted.
  - The URL path itself is incorrect — for example, a typo in the endpoint segment.

  **How to fix it**

  Double-check the full URL you are calling against the [API reference](/api-reference) to confirm the path structure is correct. Then verify that the ID you are passing belongs to a resource that exists in the target environment. Keep in mind that IDs are environment-specific — a resource ID from staging will not resolve in production.
</Accordion>

<Accordion title="422 Unprocessable Entity">
  A `422 Unprocessable Entity` response means the request reached the server and was well-formed at the HTTP level, but the body failed validation. Common causes include missing required fields, incorrect data types, and values that fall outside accepted enumerations.

  **How to fix it**

  Read the `errors` array in the response body — it identifies exactly which fields failed and why. For example:

  ```json
  {
    "error": "validation_failed",
    "errors": [
      {
        "field": "metric.unit",
        "message": "must be one of: count, percentage, duration, currency"
      },
      {
        "field": "metric.value",
        "message": "required field is missing"
      }
    ]
  }
  ```

  Cross-reference each flagged field against the [API reference](/api-reference) to confirm the correct type, format, and allowed values. Pay particular attention to enum fields, ISO 8601 date strings, and numeric fields that must not be passed as strings.
</Accordion>

<Accordion title="429 Too Many Requests">
  A `429 Too Many Requests` response means you have exceeded the rate limit for the endpoint or your account tier. The API enforces per-minute and per-hour request limits to ensure fair usage across all clients.

  **How to fix it**

  Check the `Retry-After` header in the response — it contains the number of seconds you must wait before sending another request:

  ```http
  Retry-After: 30
  ```

  Implement exponential backoff in your client so that retries wait progressively longer between attempts. A simple strategy is to double the wait time on each retry, starting from the `Retry-After` value, with a randomized jitter to prevent synchronized retry storms. See the [Rate Limits](/api-reference/rate-limits) page for full details on limits by tier and endpoint.
</Accordion>

<Accordion title="Webhook not being received">
  If events are not arriving at your webhook endpoint, work through the following checks in order:

  1. **Confirm your endpoint is publicly reachable.** The Open PMM servers must be able to send an outbound HTTPS POST to your URL. Endpoints on `localhost` or behind a firewall will not receive deliveries. Use a tool like [Webhook.site](https://webhook.site) to test reachability.

  2. **Verify the signature.** Every delivery includes an `X-OpenPMM-Signature` header. If your handler rejects the signature, ensure you are computing the HMAC using the exact raw request body — not a re-serialized version — and that you are using the correct webhook secret for the environment.

  3. **Return a 2xx status code promptly.** The Open PMM delivery system marks a delivery as failed if your endpoint does not respond with a `2xx` status within the timeout window. Move any heavy processing to a background queue and return `200 OK` immediately upon receipt.

  4. **Check the delivery log.** In the Open PMM dashboard, open your webhook configuration and inspect the delivery history. Failed deliveries show the HTTP status your endpoint returned and the full response body, which helps diagnose handler errors.

  5. **Check for TLS issues.** Your endpoint must present a valid, trusted TLS certificate. Self-signed certificates will cause deliveries to fail.
</Accordion>

<Accordion title="Cursor pagination not working as expected">
  Cursor-based pagination can behave unexpectedly if cursors are modified or reused incorrectly.

  - **Do not decode, inspect, or modify cursors.** Cursors are opaque tokens — their internal format may change without notice. Treat them as black-box strings.
  - **Always use the `next_cursor` value from the most recent response.** Do not cache cursors across sessions or share them between users, as they encode a snapshot of the result set at a specific point in time.
  - **Check for `has_more`.** When the `has_more` field in the response is `false`, you have reached the last page. Stop iterating rather than sending an empty or stale cursor.

  A correct pagination loop looks like this:

  ```typescript
  let cursor: string | undefined;

  do {
    const response = await client.resources.list({
      limit: 50,
      cursor,
    });

    process(response.data);

    cursor = response.next_cursor;
  } while (response.has_more);
  ```
</Accordion>

<Accordion title="CLI command not found after install">
  If you run an Open PMM CLI command and receive a `command not found` error, the most likely cause is that the install location is not on your system `PATH`.

  **Steps to resolve:**

  1. **Check your Node.js version.** The Open PMM CLI requires Node.js 18 or later. Run `node --version` and upgrade if needed.

  2. **Locate the install directory.** Run `npm root -g` to find where global packages are installed, then confirm that the parent `bin` directory is included in your `PATH`.

  3. **Add the bin directory to your PATH** (if it is missing):

     ```bash
     # Example for macOS/Linux — add to ~/.zshrc or ~/.bashrc
     export PATH="$(npm bin -g):$PATH"
     ```

     Then reload your shell with `source ~/.zshrc` (or the equivalent for your shell).

  4. **Reinstall the CLI.** If the above steps do not resolve the issue, uninstall and reinstall:

     ```bash
     npm uninstall -g openpmm
     npm install -g openpmm
     ```

  5. **Verify the installation** by running:

     ```bash
     openpmm --version
     ```
</Accordion>

<Info>
  If none of the solutions above resolve your issue, reach out to the Open PMM support team at [support@openpmm.io](mailto:support@openpmm.io). Include your request ID (found in the `X-Request-ID` response header), the endpoint you were calling, and a sanitized copy of your request body.
</Info>
