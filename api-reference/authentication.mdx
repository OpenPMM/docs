Every request to the Open PMM API must include a valid API key. Open PMM uses Bearer token authentication — you pass your key in the `Authorization` header of each HTTP request. There are no cookies or session tokens; each request is independently authenticated.

## Obtaining an API Key

<Steps>
  <Step title="Open your dashboard settings">
    Log in to your Open PMM account and navigate to **Settings → API Keys** from the sidebar.
  </Step>
  <Step title="Create a new key">
    Click **Generate New Key**, give it a descriptive name (e.g., `ci-pipeline` or `data-export`), and select the appropriate scope for your use case.
  </Step>
  <Step title="Copy the key immediately">
    Your key is displayed once at creation time. Copy it and store it in a secure secrets manager — Open PMM does not show the full key value again after you leave the page.
  </Step>
</Steps>

## Sending the Authorization Header

Include your API key as a Bearer token in the `Authorization` header of every request:

```bash
Authorization: Bearer <your-api-key>
```

<CodeGroup>
```bash curl
curl https://api.open-pmm.com/v1/resources \
  -H "Authorization: Bearer $OPEN_PMM_API_KEY" \
  -H "Content-Type: application/json"
```

```python Python
import os
import requests

api_key = os.environ["OPEN_PMM_API_KEY"]

response = requests.get(
    "https://api.open-pmm.com/v1/resources",
    headers={
        "Authorization": f"Bearer {api_key}",
        "Content-Type": "application/json",
    },
)

response.raise_for_status()
print(response.json())
```

```javascript Node.js
const apiKey = process.env.OPEN_PMM_API_KEY;

const response = await fetch("https://api.open-pmm.com/v1/resources", {
  headers: {
    Authorization: `Bearer ${apiKey}`,
    "Content-Type": "application/json",
  },
});

if (!response.ok) {
  throw new Error(`API error: ${response.status}`);
}

const data = await response.json();
console.log(data);
```
</CodeGroup>

## Key Scopes

When you generate a key, you assign it one of three scopes. Grant only the minimum scope your integration requires.

| Scope | Allowed Operations |
|---|---|
| `read` | `GET` requests only — fetch resources, metrics, reports, and other resources |
| `write` | All `read` operations plus `POST`, `PUT`, and `DELETE` on resources you own |
| `admin` | All `write` operations plus user management, billing, and account-level configuration |

A key with `read` scope that attempts a `POST` request receives a `403 Forbidden` response. Upgrade the key's scope in **Settings → API Keys** if you need broader access.

## Authentication Error Responses

**401 Unauthorized** — returned when the `Authorization` header is missing, malformed, or contains an invalid or revoked key:

```json
{
  "error": {
    "code": "UNAUTHORIZED",
    "message": "Missing or invalid API key. Include a valid Bearer token in the Authorization header.",
    "details": {}
  }
}
```

**403 Forbidden** — returned when your key is valid but lacks the scope required for the requested operation:

```json
{
  "error": {
    "code": "FORBIDDEN",
    "message": "Your API key does not have permission to perform this action. Required scope: write.",
    "details": {
      "requiredScope": "write",
      "currentScope": "read"
    }
  }
}
```

## Best Practices

<Warning>
  Never hardcode an API key directly in source code or commit it to version control. A leaked key provides full access to your account up to its assigned scope.
</Warning>

- **Use environment variables.** Load your key from `OPEN_PMM_API_KEY` (or your platform's secrets store) at runtime, as shown in the examples above.
- **Rotate keys regularly.** Generate a new key and revoke the old one on a schedule, or immediately if you suspect a key has been exposed.
- **Use the narrowest scope possible.** A read-only integration should never hold a `write` or `admin` key.
- **Name keys descriptively.** Names like `github-actions-deploy` or `analytics-dashboard` make it easy to audit which systems have access and revoke individual keys without disrupting others.
